Abstract

This project studies CV–JD matching when both job descriptions (JDs) and CVs are unstructured natural language. The pipeline is: local-LLM keyword extraction → keyword merging/clustering → autoencoder encoding → vector retrieval. The data contain 10 standard JD–CV pairs with the actual hired CV, plus 100 anonymised CVs, giving a 110-CV candidate pool. Keywords are extracted by a local Qwen2.5-Coder-14B-Instruct model; clustering, encoding and retrieval are non-LLM programs. The primary evaluation is leave-one-pair-out (LOPO): each fold trains on 9 GT pairs + 100 unlabelled CVs and evaluates the held-out pair. The primary metric is Recall@10, with Recall@5, MRR@10, mean rank and Wilson 95% CI.

Key result: LOPO Recall@10 = 0.800; TF-IDF baseline = 0.800; Δ = +0.000; in-sample upper bound = 1.000.

1. Task and Data

1.1 Task definition

Given a JD and a pool of CVs, the system returns the top-10 best-matching CVs. The matching signal comes only from keywords extracted from natural-language text; human match labels are never used as input features. The 10 GT pairs are used only for supervised training and evaluation.

1.2 Data

  • 10 standard JDs: the first part of each PDF in JD + Hired CV examples; natural-language descriptions.
  • 10 hired CVs: the CV OF THE HIRED CANDIDATE part of the same PDFs; one known positive per JD.
  • 100 anonymised CVs: Anonymised-CVs-100; unlabelled candidates and unsupervised training data.
  • Candidate pool: 100 + 10 = 110 CVs. The 10 hired CVs are not in the 100 anonymised CVs.
  • Excel not used: the Manatal structured tags are not used in this task.

2. Method

2.1 Local-LLM keyword extraction

We use a locally deployed Qwen2.5-Coder-14B-Instruct via LM Studio at temperature 0, with a fixed JSON schema. Each keyword has a term, category and importance (1–3). Results are cached as JSONL with resume support. Across 120 documents the extraction produced 24.5 keywords on average (range 12–46); three very long outputs were retried with a larger token budget and all became valid.

2.2 Keyword merging and clustering

Alias normalisation is followed by local Nomic keyword embeddings (a non-generative model) and cosine agglomerative clustering. Ambiguous terms such as Java/JavaScript and SQL are protected from merging. Each cluster gets a canonical term, yielding a 120-document × vocabulary TF-IDF matrix.

2.3 Autoencoder

The AE is V → 512 → 256 → 32 → 256 → 512 → V with GELU, dropout, AdamW and denoising reconstruction. A supervised listwise retrieval loss is added on the bottleneck: the hired CV is the positive and the other 109 CVs are negatives. The AE therefore learns both document representation and matching from the 10 GT pairs. A 16/32/64 bottleneck ablation favoured 32 dimensions.

2.4 Retrieval and evaluation

JDs and CVs are encoded into 32-d unit vectors and ranked by cosine similarity. The primary LOPO protocol holds out one GT pair per fold, trains on the other 9 pairs + 100 unlabelled CVs, and retrieves from the 110-CV pool. We also report an in-sample upper bound and three unsupervised baselines: TF-IDF, keyword overlap and BM25.

4.2 Main observations

  • AE matches the baselines on Recall, but has lower MRR: LOPO Recall@10 = 0.80, the same as TF-IDF / BM25; however AE MRR@10 is 0.32 (TF-IDF 0.44), so it often retrieves the right CV but ranks a similar distractor above it.
  • In-sample is strongly optimistic: 1.00 after training on all 10 pairs vs 0.80 under LOPO; 10 pairs are easy to memorise, so the report uses LOPO as the primary estimate.
  • Two misses: P04 (Data Engineer) at rank 13, a near miss with missing Azure Synapse / PySpark terms; P06 (Deployment Strategist) at rank 36, with almost zero keyword overlap because the JD is a project/customer/delivery role while the hired CV is data-science oriented.
  • Hits with low ranks: P02 (Sales Manager in Indonesia) rank 9, P07 (Marketing Manager (HK & SG)) rank 9, P09 (Tech Lead) rank 10; the positive CV shares few explicit JD keywords and is pulled into the top-10 by the latent vector, while top-1 is often a domain-irrelevant CV (e.g. P08's top-1 is a video-editing CV).
  • Synonyms remain a major error source: flavour/flavor, key account management/client relationship management, B2B sales/international sales are not fully merged, so P02/P07 positives share only one JD keyword.

5. Improvements

  • Must-have gating: use JD keywords with importance=3 as a hard gate; down-weight or filter CVs missing critical must-haves.
  • Hybrid retrieval: combine AE vectors with BM25 / keyword overlap to balance semantics and exact terminology.
  • Better normalisation: expand the skill synonym table and separate Java/JavaScript, SQL/MySQL, AWS/Azure/GCP.
  • More GT: 10 pairs are too few; add 30–50 human relevance judgments or run a pooled evaluation.
  • Category-aware encoding: encode skill/tool/domain blocks separately so generic responsibility words do not dominate hard skills.

6. Limitations

  • Only 10 GT pairs; the confidence interval is wide and the query granularity is 0.1.
  • Recall treats only the hired CV as relevant; other potentially good CVs are unlabelled, so the metric is conservative.
  • The 110-CV pool is small; results should not be extrapolated to large-scale recruiting.
  • LLM extraction has category drift and misses; no large-scale human audit was performed.

A. LLM prompt

Extract 12-25 canonical keywords...
Return JSON: doc_id, doc_type, role_title, seniority,
years_experience, location, languages, keywords[{term, category, importance}].
"languages" must contain ONLY human spoken languages.
Programming languages use category "programming_language".
