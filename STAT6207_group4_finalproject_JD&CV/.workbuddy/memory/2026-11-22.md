## 上下文长度实测（决定成败的参数）
- 最坏情况实测（全库最长 CV-022，5906 字符）：输入 5672 tok + 输出 2174 tok = **7846 tok**。
- **8K 只剩 346 tok 余量（96%）→ 有静默截断风险**；已用 `lms load ... -c 16384` 提到 16K，占用仍为 **6.55 GB**（KV cache 按需增长，不预分配），**速度不变：56.8 tok/s**，`finish_reason=stop`。
- 1.1 tok/s 的根因：LM Studio 默认上下文过大（反推 ≥32K × parallel 4），KV cache 吃满 15.6/16.3 GB → 部分层 offload 到 CPU → 每 token 都跨 PCIe 搬数据（显存带宽 ~700 GB/s vs PCIe ~25 GB/s）。**与模型能力无关，纯粹是显存装不下。**
- `extract.py` 已加截断检测：`finish_reason == "length"` 直接抛错重试，不保存残缺 JSON。

## 全量抽取的踩坑记录（重要，别再犯）
第一次全量跑：`ok=145 skip=4 fail=1`，45.5 分钟。随后发现三类问题，逐一修：
1. **evidence 拼接导致误杀**：模型把 `"Position: X\nJob Title: X"` 拼成一条 evidence，但原文里两句不相邻 → 整段匹配失败 → `position` 被置 null（5 份 JD 中招）。修法：`_snippet_ok()` 按换行/分号/竖线切段，任一段命中即通过。
2. **JSON 引号断裂**：`CV-042` 的 `description` 里有 `"Frequently Bought Together"` 裸引号，每次都在 char 2347 报错（temperature=0 输出确定，重试无用）。修法：`_repair_quotes()` 状态机——遇到引号时向后看第一个非空白字符，是 `,}]:` 才算字符串结束，否则替换成中文引号。
3. **重新校验把程序注入字段也清了**（最严重的失误）：`jd_id` / `cv_ref` 没有 evidence，被新规则当成"无依据"全部置空，连 `JD-45` 整份字段都被清掉。修法：加 `ID_KEYS` 白名单排除；并把 evidence 要求分层 —— `STRICT_FIELDS`（position/country/薪资/学历原文/公司职位）必须有证据，其余（domain/seniority/highest_degree/skills 等派生字段）有证据才校验、没有则保留。
4. **整份无 evidence 时不应清空**：`JD-45` 模型输出的 `evidence` 是空对象，导致整份被清空。修法：`evidence` 为空 dict 时跳过校验，只打 `_meta.evidence_missing` 标记供人工复核。
- 教训：**批量后处理脚本必须先在小样本上验证，并显式排除程序注入字段**。这三个 bug 都是"一次改全部"造成的，代价是两轮全量重跑。
- **最终状态（已确认）**：`extract.py --all --force` 全量重跑成功，**ok=150 fail=0**，44.5 分钟，150 个 JSON 全部有编号、JD 的 position 100%。产物在 `main/match_work/extracted/`，质量报告 `main/match_work/抽取质量报告.md`。
- 覆盖率要点：JD `position`/`contract_type` 100%、`must_have_skills` 92%、`country` 86%；CV `current_title`/`current_company`/`skills` 100%、`work_history` 97%。**预期内缺失**：`languages`（CV 仅 7%）、`notice_expectation`（6%）、`remote_allowed`（34%，原表 37/50 就空）—— 报告里要写成「数据本身没有」，不是抽取失败。

## Windows bat 的坑（2026-11-22 19:35，用户双击无反应）
- **症状**：双击 `start_web.bat` 完全没反应。
- **两个原因**：
  1. **换行符是裸 LF**（0 个 CRLF）—— 用 Write 工具写 bat 会得到 LF，而 cmd 解析 bat 必须有 CRLF，否则行被错误合并、命令静默失效。这是根因。
  2. **编码是 UTF-8 无 BOM** —— cmd 默认按 GBK 读，`title`/`echo` 里的中文变乱码字节。
- **修法**：改用 Python 以 `wb` 模式写入，`"\r\n".join(lines).encode("ascii")`，内容**全部英文**。实测：2 秒拉起服务，`/api/status` 正常返回。
- **结论：以后在 Windows 上生成 .bat，一律用 Python 写 CRLF + 纯 ASCII，不要用 Write 工具直接写 bat。**

## country 抽取错误的根因与修法（2026-11-22 20:15）
- 现象：JD-02「AI Research Scientist」推荐第一名是 HR。深挖发现 `country` 抽成 Singapore，实际是 Vietnam。
- **根因不是模型看错，是原文有两处 Location 互相矛盾**：
  ```
  L3:  Location: Ho Chi Minh, Vietnam   ← 招聘系统元信息字段
  L10: Location: Singapore              ← 正文里写的
  ```
  模型选了正文那个，而规范没规定冲突时以谁为准。另 JD-23 同样问题（Dubai vs Bahrain）。
- **修法：不再让模型决定**。新增 `main/matcher/fix_location.py`：程序正则取**第一处** `Location:` 行，用国家名单匹配（Hong Kong 必须排在 China 之前），覆盖 country/city。共修正 4 份（JD-02/07/16/23）。
- 规范同步加了一条：「禁止从货币反推国家」（SGD→新加坡、BHD→巴林这类错误），但实测光靠提示词压不住矛盾原文，程序侧兜底才是关键。
- 修正后 JD-02 的 HR 已掉出前五。
- **遗留问题**：`location` 权重 0.453 偏高（二值特征无条件加分），出现「技能命中 0/7 但同国」排第 2 的情况。可能的改法是加 skill×location 交互特征，待定。

## 训练数据的最终构造（替代原"负例"方案）
- 数据源三处：标签 `dataset_from_blackboard/llm_labelled_pairs/JD1-50_配对总表.xlsx`（H 列配对CV、L 列等级，排除"兜底"→44 组）；特征 `main/match_work/extracted/*.json`；候选池 `dataset_from_blackboard/CV_examples/`（100 份）。
- 形态：**44 个查询**，每个查询 = 1 个 JD + 100 份 CV 的候选池，其中 1 份是正例、其余 99 份是「未标注候选」（不称负例）。
- 损失：listwise softmax（ListNet 式）`L = -log( exp(s_pos) / Σ_k exp(s_k) )`，无需负例标签，未标注候选只作分母里的竞争者。
- 44 组构成：强 21 / 中 17 / 弱 6。弱匹配会引入噪声 → 做消融：只用 21 强 vs 全 44，报两者在测试集上的差异。
