# 附录：写给本地模型的提示词

本文件夹保存调用本地大模型时使用的两份提示词。它们是系统里唯一“告诉模型要做什么”的文件，
其余代码只负责调用与校验。

## 它们在程序里的角色

每次抽取一份文档，程序发出的请求由两部分组成：

    system 角色：提示词全文（本文件夹里的两份 .md）
    user 角色  ：待抽取的文档原文（JD 或简历，一字不改）

模型的输出是一段 JSON 文本，键名固定为英文，值按提示词里的规则填充。

调用参数固定为：

    temperature   = 0        （不随机，同一份文档每次结果一致）
    max_tokens    = 3000
    reasoning_effort = "none"（关闭思维链，否则输出会被推理过程包住）

## 两份提示词的分工

- 提示词_JD侧.md  —— 用于岗位描述，抽取 19 个字段（岗位、地点、薪资、技能清单等）
- 提示词_CV侧.md  —— 用于简历，抽取 14 个字段（现职、公司、技能、工作经历、学历等）

两份文件结构相同：先说明任务，再逐字段给出定义、取值规则、示例、缺失时怎么写、边界情况怎么判，
最后附 JSON 骨架与自检清单。

## 提示词里写死的几条规则

1. 只输出 JSON，不要解释、不要前后缀。
2. 每个字段附 evidence：从原文逐字复制的片段；找不到对应句子则该字段留空。
3. 空值表示“未知”，不表示“否”。简历没写城市，`country` 就留空，不得从学校、公司或电话区号反推。
4. 技能必须归一为 1–4 个词的短名词（`kubernetes` 而不是整句要求），并做别名统一（`k8s` → `kubernetes`）。
5. 枚举字段必须在白名单内；确实看不出来时留空，不得为了填满而硬凑一个值。

## 提示词之外的第二道校验

提示词只能提高模型守规矩的概率，不能保证。因此程序在收到结果后还会做一遍机械校验：
把每个字段的 evidence 回到原文逐字搜索，搜不到的字段一律置空，不进入后续打分。
这一步写在 `main/LLM_program/extract.py` 的 `verify_evidence()` 里。

## 说明

提示词本身用中文撰写，因为本地模型对中文指令的遵循度更稳；输出的 JSON 键名仍是英文，
与后续特征计算保持一致。两份文件均为副本，原始位置在 `main/LLM_program/`。

## 附：匹配器的核心权重

`权重文件_weights.json` 是程序运行时唯一依赖的模型文件，979 字节，内含三组权重：

    feature_names     11 个维度的键名（数组顺序）
    prior             人工先验，对照用，不参与排序
    learned_all44     线上使用的那组（44 组配对训练得到）
    learned_strong21  只用 21 组强匹配训练的对照版
    meta              训练记录：44 组、池 100、λ=0.05、交叉验证分数

线上那组的 11 个数值（按 feature_names 顺序）：

    必备技能重合   1.143      职级匹配       0.782
    语义相似       0.826      全文词面相似   0.695
    地点相容       0.453      学历达标       0.264
    技能覆盖率     0.256      加分技能重合   0.201
    年限达标       0.162      语言相容       0.000
    行业一致       0.000

运行时每个候选人的得分为：11 个维度的分数各自乘以对应权重后相加。
这一计算写在 `main/matcher/pipeline.py` 的 `Matcher.match()` 中。

各维度的分数如何折算到 0–1，见同目录的 `特征计算_features.py`
（例如技能重合为命中数除以总数，年限按档位给分，语义相似为向量余弦）。

权重可复现：`python main/matcher/train.py` 约 3 秒重新训练并覆盖 weights.json。
