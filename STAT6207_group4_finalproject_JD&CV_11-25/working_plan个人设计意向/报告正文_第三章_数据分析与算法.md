# 三、数据分析与算法

> 本文件是第三章的正文草稿，可直接复制到笔记或 Word 中。数字均来自本项目实跑结果。

## 3.1 数据观察：为什么需要多维特征

在设计打分方式之前，先对已抽取的标签做了三项统计，这三项统计直接决定了后面的特征选择。

第一是字段覆盖率。JD 侧 `position` 与 `contract_type` 的覆盖率达到 100%，`must_have_skills` 为 92%，`country` 为 86%，`seniority` 为 80%，起薪信息为 62%；CV 侧 `current_title`、`current_company`、`skills` 三项均为 100%，`work_history` 为 97%，`highest_degree` 为 89%，`country` 为 82%，而 `languages` 仅有 7%。这说明可用于计算的字段集中在技能、职级、年限与地点四类，语言维度因原始简历几乎不写语言能力而基本失效，这一点在最终训练出的权重中也得到了印证。

第二是正例的技能字面重合率。以 DevOps 岗位为例，JD 要求的工具是 Ansible、Terraform、CloudFormation、Jenkins、CircleCI，而实际被录用者来自 SRE 背景，掌握的是 Kubernetes、Calico、Cilium、Datadog，两者字面重合仅 1 项，重合率约 0.08。对全部 44 组配对统计，正例的技能重合率普遍落在 0.08 到 0.14 之间。这说明“岗位对得上但工具名对不上”是常态，仅靠字符串匹配无法识别这类匹配。

第三是语义相似度的分布。用本地嵌入模型对全部 JD 与 CV 两两计算余弦相似度后，均值集中在 0.64 到 0.69 之间，标准差仅 0.04 到 0.06。也就是说，同一个领域内的招聘文档彼此都很像，语义相似度本身缺少区分度，单独使用无法排序，只能作为组合特征中的一维。

以上三点共同说明：单一信号不足以判断匹配与否，必须把多种弱信号组合起来，并各自赋予合适的权重。这正是本文设计 11 维特征并对权重进行学习的出发点。

## 3.2 JD 与 CV 的结构化抽取

匹配的前提是两侧都能算出可比较的量，因此第一步是把非结构化文本转成固定字段的标签。该步骤由本地部署的大语言模型 Qwen3.5-9B 完成，模型运行在 LM Studio 提供的本地服务上，程序通过本机 HTTP 接口调用，全过程不联网，简历内容不出本机。

抽取的目标不是生成摘要，而是输出固定 schema 的结构化数据：JD 侧 19 个字段，包括岗位名称、岗位大类、国家与城市、是否允许远程、合同类型、薪资区间与币种、最低年限、职级、必备技能清单、加分技能清单等；CV 侧 14 个字段，包括当前职位、当前公司、所在国家、技能清单、工作经历（职位、公司、起止时间、职责描述）、教育背景、最高学历、行业等。所有枚举型字段均限定在预定义白名单内，技能统一转小写并做别名归一，例如 `k8s` 归一为 `kubernetes`，`gcp` 归一为 `google cloud`。

为抑制模型编造，抽取环节设置了两道约束。第一道在提示层：每个字段必须附带一段从原文逐字复制的证据片段，找不到对应句子时该字段置空。第二道在程序层：模型返回后，程序把证据片段回到原文做逐字比对，凡是对不上的字段一律置为空值，不计入后续计算。

空值的语义需要单独说明。在本系统中，空值表示“未知”，不表示“否”。例如简历通篇没有提到所在城市，`country` 字段就留空，程序在计算地点相容性时跳过该项，而不是判定为地点不符。这一点与任务书中“未标注不等于负样本”的设定一致，也是后续训练目标选择的前提。

抽取结果以 JSON 形式存入标签库，每条记录除结构化字段外还携带一个 768 维语义向量，用于后续计算语义相似度。入库只需执行一次，新增简历时只对缺标签的文件补做抽取，已有标签不会重复计算。

## 3.3 权重的训练过程

权重训练是一次性的离线步骤，输入是 44 组配对，输出是 11 个浮点数。

训练数据的构造方式是：把每一组配对视为一次检索查询，其中 JD 是查询，100 份简历构成候选池，配对关系指定了这 100 人中哪一份是正确答案。对每一个查询，先用与线上完全相同的特征函数，把 100 份候选逐一算出 11 维特征，得到 44 个形如“100 × 11”的矩阵。

训练目标是让正确答案在自己那一组候选池中的得分排名尽量靠前，采用 listwise 形式的 softmax 目标：把每组 100 个候选的得分做归一化，正确答案对应的概率越大越好。写成公式即

    max_w  Σ_{j=1..44} log( exp(w·φ(q_j, c_j+)) / Σ_{k∈pool_j} exp(w·φ(q_j, c_k)) )

其中 φ 为 11 维特征向量，w 即待学习的权重。求解采用 L-BFGS，并加入 L2 正则（λ = 0.05）抑制过拟合，整个训练过程在 3 秒内收敛。

这里需要说明为什么采用排序目标而不是二分类。二分类要求对每一个“JD-简历”对给出 0 或 1 的标签，而候选池中除了一份正确答案之外，其余 99 份并未被任何人标注过，我们既不知道它们合适，也不知道它们不合适。若强行把它们标为 0，等于凭空断言“不匹配”，与数据的实际状态不符。排序目标只要求“这一份比同池其他更好”，未标注的简历只作为竞争者出现在分母中，从头到尾没有被断言为负例，因此更符合数据的真实情况，也守住了任务书中未标注样本的处理原则。

训练完成后得到 11 个权重，保存为模型文件，其中占比较大的几项为：必备技能 1.14、语义相似 0.83、职级匹配 0.78、全文词面相似 0.69、地点相容 0.45；语言与行业两项权重为 0。行业为 0 并不表示行业不重要，而是该字段在数据中大量缺失、其余取值又只有 13 类粗粒度枚举，特征近似常数，无法从 44 组样本中学出有效权重。

由于样本量与参数量的比值仅约 4:1，训练结果存在明显的方差。5 折交叉验证显示，学出的权重在训练集内部的平均倒数排名为 0.252，略低于人工设定的先验权重 0.290；但在独立的 30 组真实录用配对构成的测试集上，学出权重反超为 0.439 对 0.307。这一反差的成因与含义在实验结果一章中讨论。

## 3.4 运行流程

权重训练完成后，程序运行阶段不再涉及任何训练，只做加载与计算。

一次查询的处理流程如下。客户提供的 JD 文本先经解析器取出纯文本，再交给本地模型抽取 19 个字段；接着读取每个字段对应的 768 维向量。随后程序遍历标签库中的全部候选人，把这份 JD 与每一份简历的标签配对，算出 11 个分数：必备技能重合率、加分技能重合率、技能集合覆盖率、年限达标程度、职级匹配程度、地点相容性、学历达标程度、语言相容性、行业一致性、全文词面相似度、语义相似度。每个分数都归一化到 0 至 1 之间，缺失项取中性值而不取 0。

最后用训练得到的 11 个权重做加权求和，得到该候选人的总分，全库排序后取前 5 名输出。每条结果附一句推荐理由，理由由计算过程中已有的事实拼装而成，例如“必备技能命中 7/12（aws、ansible、docker、github actions）；7.1 年经验（要求 3 年）；职级 mid”，不含任何由模型自由生成的主观评价。

这一阶段有两个工程性质需要强调。其一是训练与推理共用同一套特征计算代码，避免出现训练时和运行时“算的不是同一个东西”的偏差。其二是运行时不需要 GPU 做大模型推理以外的任何计算，100 余份候选的特征计算与排序在零点几秒内完成，整体耗时几乎全部来自第一步的 JD 抽取。

综上，系统由两个彼此独立的阶段组成：离线阶段从 44 组配对中学出 11 个权重并固化为模型文件，在线阶段加载该文件，把任意一份 JD 与库中候选人逐项比较并排序。前者只执行一次，后者每次查询执行。
